# LegacyBox architecture

LegacyBox is split into trust boundaries so save-writing and network code cannot silently change provenance.

## 1. Manifest layer

A living-dex manifest describes the desired species/form, target level, and the encounter template that should be used as the source of truth.

A template reference is not itself proof of legality. The legality backend must resolve and verify it.

## 2. Generation layer

A future candidate generator will resolve a template and produce a native-format candidate such as PK7. Generation must be deterministic when given the same template and seed.

Generated artifacts will carry:

- manifest entry key;
- template identifier;
- generator version;
- hash of the generated bytes;
- validation result.

## 3. Legality layer

The legality interface is deliberately pluggable. The bootstrap backend returns `UNVERIFIED` for every entry. This prevents a placeholder implementation from being mistaken for a legality checker.

A production backend must verify at least:

- species/form and origin game;
- encounter method, met location, and met level;
- PID/EC constraints where applicable;
- ability, gender, nature, IVs, and EVs;
- moves/relearn moves;
- ball;
- OT/TID/SID and language;
- ribbons/fateful encounter/event constraints;
- evolution history.

## 4. Vault layer

Any imported Pokémon or save is stored immutably before transformation. Derived versions reference the original hash rather than replacing it.

## 5. Save layer

Save modification is a separate boundary:

1. read source save;
2. hash and back it up;
3. validate candidate;
4. write to an empty/selected slot;
5. repair checksums/signatures required by the format;
6. re-open and verify the modified save;
7. only then permit export back to hardware.

## 6. Device bridges

### 3DS

A homebrew client will expose a small authenticated LAN protocol for inventory, receive/send, backup, and write operations.

### iOS

The iOS client is the vault browser and transfer controller. It should discover the 3DS bridge over Bonjour/mDNS and use an authenticated encrypted session.

## 7. HOME/Bank boundary

LegacyBox will not invent HOME tracker values or Bank server history. Where an official transfer path exists, the project hands a validated game/save state to the official client and treats the server transaction as outside LegacyBox.


## 8. Provenance trust boundary

LegacyBox separates four independent concepts:

1. source/origin evidence;
2. local PKM legality;
3. observed or user-confirmed official Bank migration;
4. observed HOME tracker/server provenance.

A generated candidate may pass local legality and later traverse the official Bank->HOME path without becoming historically legitimate at its original encounter. Likewise, a nonzero HOME tracker is evidence that must be recorded but cannot be authenticated locally.

See `docs/HOME_PROVENANCE.md`.


## 9. Official Bank handoff

LegacyBox3DS automates only the local preparation boundary:

```
validated PK7 batch
  -> LBX1 SD bundle
  -> LegacyBox3DS hash verification
  -> Gen VII save injection
  -> normal save commit
  -> official Pokémon Bank application
```

The official Pokémon Bank application remains the only component that authenticates to Nintendo and talks to the Bank service. LegacyBox does not proxy, emulate, or reverse-engineer Bank's private network/authentication protocol.

The initial save-writing adapter uses PKSM's public script API because PKSM already supports Gen VII save access and PKX injection on CFW. The standalone LegacyBox3DS writer is a later milestone and will preserve the same fail-closed/no-overwrite semantics.
